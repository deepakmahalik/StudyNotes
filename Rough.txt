Exact Steps to Run RAG + DB
Step 1 — Start Qdrant (Vector DB)
Open a terminal and run:

docker run -p 6333:6333 qdrant/qdrant
Qdrant dashboard will be available at: http://localhost:6333/dashboard

Step 2 — Start the Flask App
Open a second terminal:

cd C:\OtherProjects\StudyNotes
uv run python Backend/app.py
App runs at: http://localhost:5000

Step 3 — Login
Go to http://localhost:5000/login and log in with:

username: admin
password: admin
Step 4 — Save Your Mind Map
In the UI, create or load your nodes and click Save. This stores them in SQLite (database.db).

Step 5 — Ingest Nodes into Qdrant
Run this once after saving (use Postman, curl, or browser fetch):

curl -X POST http://localhost:5000/api/rag/ingest \
  -H "Content-Type: application/json" \
  --cookie "session=<your-session-cookie>"
Or from the browser console (while logged in):

fetch('/api/rag/ingest', { method: 'POST' })
  .then(r => r.json()).then(console.log)
Expected response:

{ "message": "Ingestion complete", "status": "ok", "chunks_indexed": 12 }
Step 6 — Chat with RAG
curl -X POST http://localhost:5000/generate-text \
  -H "Content-Type: application/json" \
  -d '{"text": "What topics do I have in my mind map?", "session_id": "s1"}'
Response will include:

{
  "type": "chat",
  "message": "Your mind map contains...",
  "sources": ["Node: Machine Learning", "Node: Python"],
  "mode": "rag"
}
Step 7 — Check RAG Stats (Admin)
fetch('/api/rag/stats').then(r => r.json()).then(console.log)
Re-ingest Rule
Every time you update and save your mind map, call /api/rag/ingest again to keep Qdrant in sync.

The video focuses on the fundamental concepts and practical application of evaluating generative AI and RAG (Retrieval-Augmented Generation) systems.

### Core Evaluation Concepts

  * **Challenges in Evaluation:** Unlike traditional, deterministic software that can be evaluated using standard unit testing and assertions, generative AI systems are probabilistic and produce variable responses, making testing more complex.
  * **Dimensions of Evaluation:**
      * **Functional:** Ensures output accuracy, faithfulness, and the absence of hallucinations.
      * **Cost:** Monitors token usage, monthly API bills, and system latency to ensure productivity gains are not offset by high costs.
      * **Safety:** Involves implementing guardrails to prevent toxic outputs, PII (Personally Identifiable Information) leaks, and jailbreaks.
  * **Testing Approaches:**
      * For functional evaluation, systems can use cosine similarity between the actual output and an expected "ground truth" using embeddings to determine if the responses are semantically similar.
      * Developers can integrate these tests into CI/CD pipelines to automate verification.
      * Cost management involves utilizing dashboard monitoring and budget alerts provided by cloud platforms.

### Implementation and Tools

  * **Evaluation Platforms:** The session highlights **LangSmith** (part of the LangChain ecosystem) for observing, evaluating, and deploying agents, and **Ragas** for measuring specific metrics.
  * **Ragas Framework:**
      * This library is used to manage test datasets and evaluate RAG pipelines using an "LLM-as-a-judge" approach.
      * Key metrics include **Faithfulness** (ensuring the answer is derived from the context), **Answer Relevancy**, **Context Precision**, and **Context Recall**.
      * Practical implementation involves creating a dataset containing questions, retrieved context, generated answers, and ground truths to benchmark the system.
  * **Engineering Considerations:**
      * The field of AI evaluation is rapidly evolving; developers should be prepared to write custom "glue code" to bridge gaps between frameworks and specific model providers (such as Groq).
      * Production-grade systems should treat evaluation test cases as modular building blocks, similar to Lego bricks, which can be stored in databases or version-controlled repositories.
      * A "good" score is subjective but generally, in agentic applications, a cumulative score above 60% is considered effective.

This video provides a structured guide to **RAG (Retrieval-Augmented Generation) evaluation**, explaining why traditional NLP metrics are insufficient and how modern frameworks bridge that gap.

### 1. Traditional Evaluation Metrics (0:30 - 5:10)
These metrics are designed for fixed reference answers, primarily measuring text overlap:
* **BLEU (Bilingual Evaluation Understudy):** Measures *n-gram* overlap between generated and reference text. Includes a *brevity penalty* to discourage overly short answers (0:32 - 2:08).
* **ROUGE (Recall-Oriented Understudy for Gisting Evaluation):** Focuses on *recall*—how much of the core information in the reference is present in the output. Ideal for summarization (2:09 - 3:35).
* **F1 Score:** The harmonic mean of precision and recall. It is highly effective for tasks where specific facts or entities are the priority, rather than word-for-word phrasing (3:36 - 5:09).

### 2. The Need for RAG-Specific Metrics (5:10 - 6:00)
RAG systems operate in two stages: **retrieval** and **generation**. Because RAG relies on external context to generate answers, traditional metrics fail to measure the quality of these specific stages.

### 3. Key RAG Evaluation Metrics (6:07 - 9:19)
To evaluate RAG effectively, we look at both how well the system finds information and how well it synthesizes it:
* **Context Precision:** Measures how much of the retrieved information is actually relevant to the user query (how much extra added)
* **Context Recall:** Measures the retriever’s ability to pull *all* necessary information from the database (How much information missed).
* **Answer Relevance:** Uses embeddings to assess if the generated answer directly addresses the user's intent (7:34 - 8:06).
* **Faithfulness:** Ensures the answer is strictly grounded in the retrieved context, preventing hallucinations (8:07 - 8:39).
* **Groundedness:** Evaluates if the answer relies on the retrieved documents rather than the model's internal memory (8:40 - 9:19).

### 4. Modern Evaluation Workflow (9:20 - 12:19)
* **LLM-as-a-Judge:** Since calculating metrics like faithfulness requires semantic understanding, developers use a large language model to act as an evaluator, mimicking human judgment (9:20 - 10:16).
* **RAGAS (RAG Assessment):** This open-source framework standardizes the evaluation pipeline. It automates the calculation of context precision, context recall, faithfulness, and answer relevance using a combination of embeddings and LLM-based scoring (10:17 - 12:19).
